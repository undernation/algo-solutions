# 블록 구역 관리 — 사용자 코드 상세 해설

사용자가 제공한 코드의 동작 설명이며, 논리를 변경하지 않았다. 구현은 좌표별 변 목록, Union-Find, 버전을 붙인 우선순위 큐를 사용한다.

이 풀이에서 중요한 입력 조건은 **블록이 랜덤하게 생성된다는 것**이다. 사용자는 이 조건에서 같은 좌표에 변이 많이 몰릴 가능성이 낮다고 보고, 해당 좌표의 짧은 목록을 직접 순회하는 방식을 선택했다. 이 판단을 풀이의 성능 전제로 삼아 설명한다.

문제는 기억을 바탕으로 복원되었다. 면적과 블록 수까지 같으면 구역 ID 오름차순으로 정렬한다는 조건은 아직 가정이며, 설명과 검증도 이를 따른다.

## 1. 보드 전체 대신 네 변을 관리하는 이유

채점기가 `init`, `addBlock`, `isSameRegion`, `top10`을 호출하는 함수형 API 문제다. 이 코드는 표준입력을 읽지 않고, 호출 사이에 전역 상태를 유지한다. `init`은 이전 테스트의 상태를 비운다.

보드 한 변이 45,000이면 칸은 2,025,000,000개지만, 추가 블록은 최대 15,000개로 기억된다. 모든 칸을 저장하거나 칠하면 보드 넓이에 비례하는 비용이 든다.

필요한 정보는 새 블록과 기존 블록의 접촉 여부다. 내부가 겹치지 않는 사각형은 같은 직선 위의 변이 양의 길이로 닿을 때 연결된다. 블록마다 네 변만 저장하면 된다. 면적은 `(x2 - x1) * (y2 - y1)`이며 꼭짓점 좌표이므로 `+1`을 붙이지 않는다.

구역 면적은 구성 블록의 면적 합이다. 내부 중복이 없고 공유하는 변의 면적은 0이므로 겹친 넓이를 빼지 않는다.

## 2. x_edges와 y_edges가 담는 정보

`x_edges[x]`는 x좌표가 고정된 세로변 목록이고, 각 항목은 `(y시작, y끝, 블록인덱스)`다. `y_edges[y]`는 y좌표가 고정된 가로변 목록이며, `(x시작, x끝, 블록인덱스)`를 담는다.

| 새 블록의 변 | 확인할 기존 목록 | 비교할 구간 |
| --- | --- | --- |
| x = x1인 세로변 | `x_edges[x1]` | y1부터 y2까지 |
| x = x2인 세로변 | `x_edges[x2]` | y1부터 y2까지 |
| y = y1인 가로변 | `y_edges[y1]` | x1부터 x2까지 |
| y = y2인 가로변 | `y_edges[y2]` | x1부터 x2까지 |

예를 들어 `(2, 1)–(5, 4)`인 블록은 x=2와 x=5 목록에 `(1, 4, idx)`를 넣고, y=1과 y=4 목록에 `(2, 5, idx)`를 넣는다. 좌표를 고정하는 축과 구간을 비교하는 축이 서로 다르다는 점이 핵심이다.

각 목록은 일반 리스트다. 새 블록과 고정 좌표가 같은 네 목록만 처음부터 끝까지 검사한다. **랜덤하게 생성된 블록의 변이 여러 좌표에 분산되면 각 목록이 짧아지므로, 이 단순한 순회 방식으로 빠른 처리를 기대할 수 있다.** 보드의 모든 블록을 매번 훑는 방식과 실제 검사량이 크게 달라지는 이유다.

구역이 합쳐져도 원래 변은 지우지 않는다. 변에는 블록 인덱스를 저장하고 현재 구역은 Union-Find로 찾는다. 접촉 판정의 정확성은 비겹침 조건에서 나오고, 목록을 순회해도 빠를 것이라는 성능 판단은 랜덤 생성 조건에서 나온다.

## 3. 접촉 판정식과 양쪽 방향을 섞어도 되는 이유

같은 직선 위의 두 구간 `[a, b]`, `[c, d]`가 양의 길이로 겹치는 조건은 다음과 같다.

```python
max(a, c) < min(b, d)
# 위 식과 같은 조건
a < d and c < b
```

세로변에서는 `y1 < oy2 and oy1 < y2`, 가로변에서는 `x1 < ox2 and ox1 < x2`다. x와 y를 섞지 않는다. 세로변은 같은 x의 목록을 고른 뒤 y구간을 비교한다.

`[1, 4]`와 `[3, 6]`은 길이 1만큼 겹쳐 접촉한다. `[1, 4]`와 `[4, 6]`은 끝점만 같아 연결되지 않는다. 따라서 `<`를 `<=`로 바꾸면 꼭짓점 접촉까지 합치는 오류가 생긴다.

이 코드는 한 x목록에 왼쪽 변과 오른쪽 변을 함께 넣는다. 그래도 정확한 이유는 블록의 내부가 겹치지 않는다는 전제다. 왼쪽 변끼리 같은 x에 있으면서 y구간도 양의 길이로 겹친다고 가정하자. 두 사각형 모두 그 x의 오른쪽으로 양의 폭을 가지므로 내부가 겹친다. 이는 입력 조건에 어긋난다. 오른쪽 변끼리도 같은 논리가 성립한다.

따라서 찾아낸 양의 구간 겹침은 반대 방향 변 사이의 올바른 접촉이다. 가로변도 같다. 이는 선형 스캔의 정확성 근거이며, 목록의 구간들이 서로 겹치지 않는다는 뜻은 아니다. 접촉한 두 블록의 반대 방향 변은 같은 구간을 차지할 수 있다.

## 4. 블록 ID, 내부 인덱스, 구역 ID의 차이

블록 ID는 순서대로 들어오지 않는다. `block_to_idx[blockId] = idx`로 외부 ID를 0, 1, 2, …의 내부 인덱스에 연결한다. 배열 접근과 연결 조회에는 변환한 인덱스를 쓴다.

Union-Find 대표는 구역을 관리하는 내부 인덱스다. 문제의 구역 ID는 원래 블록 ID의 최솟값이며 대표와 같을 필요가 없다. 둘을 분리하면 작은 ID를 대표로 강제하지 않고 작은 집합을 큰 집합 아래에 붙일 수 있다.

| 배열 | 대표 인덱스에서의 의미 |
| --- | --- |
| `parent` | Union-Find 부모 |
| `uf_size` | 병합 방향을 결정하는 집합 크기 |
| `region_area` | 구역 면적의 합 |
| `region_count` | 구역의 블록 수 |
| `region_id` | 구역의 최소 블록 ID |
| `version` | 해당 대표의 병합 상태를 구분하는 번호 |

`find`는 부모를 부모의 부모로 바꾸며 올라가 경로를 줄인다. `union`은 두 대표를 찾고 `uf_size`가 작은 쪽을 큰 쪽 아래에 붙인다. 면적과 개수는 더하고 최소 ID는 `min`으로 갱신한다. 집계는 현재 대표의 값만 사용하므로 흡수된 대표의 배열 값을 지울 필요는 없다.

이 코드에서는 `uf_size`와 `region_count`가 둘 다 블록 수여서 같은 값으로 증가한다. 전자는 병합 방향을 정하는 데, 후자는 순위를 매기는 데 사용하도록 역할을 나누어 표현했다.

## 5. addBlock이 처리하는 순서

먼저 새 블록을 혼자 있는 구역으로 만든다. 부모는 자기 자신, 면적은 직사각형 넓이, 개수와 크기는 1, 최소 ID는 입력 ID, 버전은 0이다. 그다음 네 좌표 목록을 검사하여 접촉하는 기존 블록 인덱스를 `neighbors` 집합에 모은다.

여기서 집합이 제거하는 것은 같은 **블록 인덱스**의 중복이다. 같은 구역에 속한 서로 다른 블록 인덱스는 모두 남을 수 있다. 구역 면적을 두 번 더하지 않게 하는 장치는 `union` 내부의 `ra == rb` 검사다.

```python
root = idx
for other_idx in neighbors:
    root = union(root, other_idx)
root = find(root)
```

`root`는 병합 결과를 따라 바뀐다. 이미 합쳐진 구역의 다른 블록을 만나면 두 대표가 같아서 집계를 더하지 않는다. `set` 순회 순서와 대표 선택이 달라도 최종 연결 관계, 합계, 최소 ID는 같다.

모든 병합을 끝낸 뒤 최종 순위 정보를 힙에 한 번만 넣는다. 중간 상태는 넣지 않는다. 마지막으로 네 변을 저장하고 최종 구역 면적을 반환한다. 자기 변을 검색 뒤에 등록하므로 자기 자신을 이웃으로 찾지도 않는다.

## 6. 순위 튜플과 버전으로 오래된 상태 구별하기

힙에는 다음 튜플을 저장한다.

```python
(-region_area[root], region_count[root],
 region_id[root], root, version[root])
```

`heapq`는 작은 튜플부터 꺼낸다. 음수 면적 덕분에 큰 면적이 먼저 나오며, 이어 블록 수와 최소 ID가 작은 순서다. 뒤의 대표와 버전은 유효성 확인용이다. 서로 다른 구역은 최소 ID도 달라 마지막 두 값이 순위를 바꾸지 않는다.

구역이 합쳐질 때 힙 속 예전 항목을 직접 찾아 수정하지 않는다. 새 상태를 추가하고, 꺼낼 때 다음 두 조건으로 예전 항목을 버린다.

```python
if parent[root] != root:
    continue
if version[root] != ver:
    continue
```

첫 검사는 대표가 흡수되었는지 확인한다. 흡수된 대표의 버전은 그대로일 수 있어 버전 검사만으로는 부족하다. 반대로 대표를 유지하며 다른 구역을 흡수하면 부모는 자신이다. 이때는 버전 검사로 예전 면적·개수의 항목을 버려야 한다.

성공한 병합마다 살아남은 대표의 버전을 1 올린다. 흡수된 대표의 버전까지 올릴 필요는 없다. 부모 검사에서 이미 탈락하고, 삭제나 분할이 없으므로 다시 대표가 되지도 않기 때문이다. `init`에서는 배열과 힙을 함께 비워 이전 테스트의 버전이 섞이지 않게 한다.

## 7. top10은 꺼낸 유효 항목을 다시 넣는다

`top10`은 힙에서 순서대로 꺼내면서 유효한 항목만 `selected`에 담는다. 오래된 항목을 열 개 꺼냈더라도 반환할 구역 열 개를 찾은 것이 아니다. 유효한 항목이 열 개 모이거나 힙이 빌 때까지 계속한다.

선택된 항목은 여전히 현재 상태이므로 힙에 다시 넣는다. 생략하면 조회만 했는데 구역이 사라져 다음 조회가 틀린다. 꺼낸 항목을 한 번씩 돌려놓으므로 중복 생성도 아니다.

새 구역은 한 번 등록되고, 변경된 구역은 이전 상태가 무효화된 뒤 최종 상태만 등록된다. 따라서 현재 구역별 유효 항목은 하나씩 유지된다.

반환값은 `Result(len(ids), ids)`이며 `ids`는 새 리스트다. 빈 보드면 개수 0과 빈 리스트, 구역이 열 개 미만이면 실제 개수만 반환한다. 각 구역의 최소 ID를 순위순으로 넣는다.

## 8. 예제로 연결과 순위 변화를 따라가기

예제처럼 N=20으로 시작한다.

| 추가 ID | 좌표 | 추가 후 해당 구역 | 반환 면적 |
| --- | --- | --- | --- |
| 20 | (0,0)–(2,2) | {20}, 구역 ID 20 | 4 |
| 7 | (4,0)–(6,2) | {7}, 구역 ID 7 | 4 |
| 15 | (2,0)–(4,1) | {20,7,15}, 구역 ID 7 | 10 |
| 3 | (6,2)–(8,4) | {3}, 구역 ID 3 | 4 |
| 9 | (6,0)–(8,2) | 다섯 블록, 구역 ID 3 | 18 |

15번은 20번의 오른쪽 변 일부와 7번의 왼쪽 변 일부에 닿는다. 넓이 2인 새 블록이 넓이 4인 두 구역을 연결해 10이 된다. 3번은 7번과 꼭짓점 (6,2)만 공유하므로 별도 구역이다. 이때 `top10`의 ID 목록은 `[7, 3]`이다.

9번은 7번과 세로변으로, 3번과 가로변으로 접촉한다. 넓이 10인 구역과 넓이 4인 구역에 자신의 넓이 4를 더해 18이 되고, 최소 ID는 3이다. `top10`은 `[3]`을 반환한다.

![ID 9가 두 구역을 연결하여 구역 ID 3, 면적 18이 되는 예제](../../problems/swea/img/99996_3.svg)

9번을 추가할 때 네 목록에서 일어나는 검사는 다음과 같다.

| 검색 목록 | 접촉 판정 |
| --- | --- |
| `x_edges[6]` | 7번과 y구간 [0,2]가 겹쳐 접촉 |
| `x_edges[8]` | 3번의 y구간 [2,4]와 끝점만 같아 제외 |
| `y_edges[0]` | 양의 길이로 겹치는 기존 x구간 없음 |
| `y_edges[2]` | 3번과 x구간 [6,8]이 겹쳐 접촉. 7번은 끝점만 같아 제외 |

버전은 특정 대표 번호를 가정하지 않고 보면 쉽다. 이전 항목이 `(…, r, v)`일 때 r이 대표로 남아 병합하면 버전이 v보다 커져 탈락한다. r이 흡수되면 부모 검사로 탈락한다. 새 항목은 모든 병합이 끝난 대표와 버전을 기록한다. 최종 버전 숫자는 병합 도중 살아남은 대표에 영향을 받으므로, 면적이나 블록 수처럼 외부에서 고정해 기대하는 값이 아니다.

## 9. 랜덤 생성 조건에서의 성능과 복잡도

정확성은 세 단계로 정리된다. 첫째, 같은 고정 좌표와 엄격한 구간 겹침으로 실제 변 접촉을 빠짐없이 찾는다. 둘째, 접촉한 블록의 구역을 Union-Find로 합치므로 직접 접촉과 간접 연결이 모두 반영된다. 셋째, 현재 대표·버전의 힙 항목만 선택하므로 정렬된 현재 구역 목록을 반환한다.

B를 추가된 블록 수라 하자. 좌표 목록은 각각 N+1개이고, 변 항목은 블록마다 네 개다. ID 사전, Union-Find 배열, 힙, 임시 이웃 집합도 O(B)이므로 공간은 **O(N+B)**다. 보드 면적에 비례하는 O(N²)이 아니다.

| 함수 | 비용 |
| --- | --- |
| `init` | 새 좌표 목록 생성 O(N) |
| `addBlock` | O(L + k·α(B) + log(B+1)) |
| `isSameRegion` | 상각 O(α(B)) |
| `top10` | O(1 + (s+10)·log(B+1)) |

L은 이번에 검사한 네 목록의 항목 수, k는 찾은 서로 다른 접촉 블록 수, s는 이번 조회에서 제거한 오래된 힙 항목 수다. α는 Union-Find 분석에 쓰는 매우 느리게 증가하는 함수다. 실제 런타임에서는 `init`에 이전 상태를 해제하는 비용도 더해진다.

`top10` 한 번이 언제나 열 개만 꺼내는 것은 아니다. 다만 오래된 각 항목은 제거된 뒤 돌아오지 않는다. B≥1이면 Q번 조회 전체의 힙 처리 비용은 O((B+10Q)·log(B+1))로 묶을 수 있다. 빈 보드의 조회는 한 번에 O(1)이다.

이 문제에서 성능을 판단할 때는 **랜덤 생성 조건을 함께 봐야 한다.** 사용자의 접근은 네 목록의 총 길이 L이 실제 입력에서 작을 것으로 기대하는 방식이다. L이 작게 유지되면 변 검색은 가볍고, 이후 Union-Find와 힙 갱신 비용이 중심이 된다. 그래서 B만 보고 매번 B개를 검사한다고 판단하면 이 풀이의 의도를 놓친다.

참고로 입력의 분산을 전혀 가정하지 않고 같은 좌표에 변을 계속 모으면 전체 검사 횟수는 Θ(B²)가 될 수 있다. 이는 일반적인 최악 경우의 분석이며, 문제의 랜덤 생성 입력에서 예상하는 성능과 구분한다. 정확한 기대 시간의 식이나 공식 시간 제한 통과 여부를 확정하려면 원래 난수 분포와 블록 크기 제한이 더 필요하다.

## 10. 실제 검증 결과와 해석 범위

CPython 3.13.3과 PyPy 3.7.10에서 각각 고정 사례 25개와 무작위 사례 1,200개를 통과했다. 각 실행에서 `addBlock` 22,200회, `isSameRegion` 971,089회, `top10` 38,561회를 비교했다. 예제 4개도 분리된 main/solution 방식과 아카이브의 코드 결합 방식 모두 통과했다.

비교 정답은 작은 보드의 정수 단위칸을 채운 뒤 상하좌우 flood fill로 구역을 다시 계산했다. 검사기는 공개 API와 Result 필드만 사용하며, 이 구현의 변 목록이나 Union-Find 내부 값을 정답 근거로 사용하지 않았다. 최대 좌표, 최대 면적 2,025,000,000, 반복 조회, 반환 리스트 변경의 영향도 별도로 확인했다. 이는 복원한 계약에서의 기능 검증이며 공식 숨은 입력 전체의 증명은 아니다.

### 넓게 분산된 랜덤 입력 50케이스

랜덤 생성 조건에서 네 좌표 목록이 얼마나 짧아지는지 별도로 측정했다. N=45,000에서 케이스마다 15,000개씩, 총 750,000개의 블록을 생성했다. 가로와 세로는 각각 1~30 중 균일하게 고르고, 그 크기의 블록이 보드 안에 들어가는 시작 좌표를 균일하게 골랐다. 기존 블록과 내부가 겹치면 다시 뽑았다. 고정 seed는 20260919다. 이는 설명을 위해 정한 자체 분포이며, 원문의 정확한 분포나 크기 제한을 복원한 것은 아니다.

| 측정 항목 | 결과 |
| --- | --- |
| 네 목록에서 검사한 변 항목 합계 | 999,012개 |
| 추가당 평균 검사량 | 1.332개 |
| 추가당 최대 검사량 | 13개 |
| 추가당 검사량의 99백분위 | 6개 |
| 단일 좌표 목록 최대 길이 | x 목록 7개, y 목록 8개 |
| CPython 3.13.3, 50케이스 합계 | 1.697초 |
| PyPy 3.7.10, 50케이스 합계 | 1.457초 |

사용자 코드를 그대로 실행했고, 두 런타임은 같은 데이터와 기대값을 사용했다. 추가 150회마다 `top10`과 `isSameRegion`을 한 번씩 호출해 각각 총 5,000회 확인했다. 시간은 `init` 50회, 추가 750,000회, 두 조회 함수와 반환값 비교를 포함한다. 데이터 생성, 기대값 계산, 통계 수집, 파일 읽기와 프로세스 시작은 제외했다. 큰 입력의 기대값은 별도 참조 구현으로 계산했으며, 앞의 작은 보드 flood fill 대조와는 구분된다.

이 분포에서는 실제로 검사하는 목록이 매우 짧았다. 따라서 **랜덤 생성으로 좌표가 넓게 분산될 때 단순한 네 목록 순회가 실용적이라는 사용자의 판단**을 확인할 수 있다. 기존 구역과 합쳐지는 추가는 365회였다. 접촉이 드문 이 측정의 실행 시간과 원래 문제의 50케이스·6초 통과 여부는 같은 주장으로 볼 수 없지만, 적어도 이 분포에서 좌표 목록 순회가 병목은 아니었다.
